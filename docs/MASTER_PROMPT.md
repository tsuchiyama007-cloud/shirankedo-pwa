# 0. この文書について

あなたは、スマートフォン向けゲーム「知らんけど」の開発を担当するAI開発エージェントです。

本ドキュメントを開発上の基本指示書として使用してください。

ゲーム仕様の詳細は `GAME_SPEC.md` を参照してください。

本プロジェクトでは、人間の開発者がプログラミング初心者であることを前提とします。

そのため、

-   分かりやすいコード
-   保守しやすい構造
-   後から機能追加しやすい設計
-   エラーが発生した場合に原因を特定しやすい設計
-   AIが継続的に開発しやすい構造

を最優先してください。

# 2. ゲームコンセプト

ゲームの基本コンセプトは、

「何をするゲームなのか分からないゲーム」

である。

プレイヤーに特定の目的を強制しない。

プレイヤーは、

-   お金を稼ぐ
-   遊ぶ
-   探索する
-   アイテムを集める
-   図鑑を埋める
-   ミニゲームをする
-   ランダムイベントを楽しむ
-   何もしない

など、自由な遊び方を選択できる。

ゲーム内の重要なキーワードは、

「自由」 「予測不能」 「偶然」 「ネタ」 「収集」 「知らんけど」

である。

# 4. 最重要開発ルール

以下を必ず守ること。

## 4.1 勝手に仕様変更しない

GAME_SPEC.md に記載された仕様を勝手に変更しない。

1.  問題点を説明
2.  変更理由を説明
3.  変更案を提示
4.  承認を待つ

必ず小さな単位で実装する。

「全部のゲームシステムを一気に実装する」

1.  プロジェクト作成
2.  タイトル画面
3.  ホーム画面

5.  セーブ
6.  運試し

# 8. コーディング方針

コードは初心者でも読めることを優先する。

以下を守る。

-   クラス名を分かりやすくする
-   変数名を分かりやすくする
-   1クラスに責務を詰め込みすぎない
-   マジックナンバーを避ける
-   コメントを適切に記述する
-   不要なコードを書かない
-   将来変更する値は設定値として分離する

# 9. シングルトンについて

Unityでは便利だからという理由だけで大量のSingletonを使用しない。

GameManagerなど本当に全体から参照する必要があるものに限定する。

可能な部分は依存関係を明確にする。

# 13. お金の処理ルール

お金を変更する場合は、直接、

    money += 100;

などを各所で乱用しない。

CurrencyManagerなどを経由する。

例：

    AddMoney()
    SpendMoney()
    CanAfford()

などを用意する。

これにより、

-   所持金不足
-   ログ
-   セーブ
-   将来のランキング
-   不正対策

などを管理しやすくする。

# 19. 運試し

# 20. 運試しの抽選

抽選結果はデータ化する。

例：

    10円
    50円
    100円
    500円
    1000円
    10000円
    100000円
    1000000円
    アイテム
    特殊イベント
    何も起きない

確率は設定値として変更可能にする。

# 21. 抽選の公平性

抽選は明確な乱数処理を使用する。

画面上の演出と実際の結果を分離する。

つまり、

    結果を先に決定
    ↓
    演出を再生
    ↓
    結果を表示

とする。

演出によって結果が変わる設計は禁止する。

# 22. 運試し演出

    ↓

# 32. セーブ失敗

保存に失敗した場合、

    データを保存できませんでした。
    もう一度試してください。

と表示する。

ゲームを強制終了させない。

# 33. ロード失敗

ロード失敗時：

1.  メインデータを確認
2.  バックアップを確認
3.  復旧可能なら復旧
4.  不可能ならユーザーに通知

勝手に初期化してデータを消してはいけない。

# 34. 設定

    SE
    バイブレーション
    通知

# 35. UI設計

基本的にスマートフォン縦持ちを想定する。

ボタンは指で押しやすい大きさにする。

重要な操作について、

-   小さすぎる文字
-   小さすぎるボタン
-   画面端ギリギリのボタン

を避ける。

# 36. UIデザイン

雰囲気：

「親しみやすい」 「ちょっとふざけている」 「見やすい」
「ごちゃごちゃしすぎない」

高級感よりも、

「何となく触りたくなる」

ことを優先する。

# 37. 「知らんけど」らしさ

ゲーム内の文章には適度にユーモアを入れる。

ただし、すべての文章に「知らんけど」を付けてくどくしない。

重要な場面で使用する。

例：

    たぶん大丈夫です。

    知らんけど。

# 38. エラー画面

ユーザーに技術的なエラー内容をそのまま見せない。

悪い例：

    NullReferenceException

良い例：

    予想外のことが起きました。

    知らんけど。

    [もう一度試す]

開発者向けログには詳細を残す。

# 39. ログ

開発中はDebug.Log等を適切に使用する。

ログには、

    [GameManager]
    [SaveManager]
    [EventManager]
    [ItemManager]

など、発生元が分かる情報を付ける。

リリース版では不要な大量ログを削減する。

# 40. クラッシュ対策

以下を重点的に確認する。

-   NullReferenceException
-   存在しないデータへのアクセス
-   存在しないアイテムID
-   存在しないイベントID
-   セーブデータ破損
-   画面遷移中の二重入力
-   高速連打
-   アプリ中断
-   アプリ復帰
-   低メモリ環境

# 41. ボタン連打対策

重要ボタンは、

    押す
    ↓
    処理開始
    ↓
    ボタン無効化
    ↓
    処理完了
    ↓
    ボタン再有効化

とする。

二重実行による、

-   二重報酬
-   二重消費
-   二重イベント

を防ぐ。

# 42. アプリ中断

-   ホーム画面へ移動
-   着信
-   他アプリ起動
-   画面OFF

などが発生する。

アプリが一時停止してもゲームデータが破損しないようにする。

# 44. 広告

# 45. 広告SDK

広告SDKはゲーム本体のロジックから分離する。

例えば、

    AdManager

を用意する。

ゲーム側は、

    AdManager.ShowRewardedAd()

などを呼ぶだけにする。

これにより広告サービス変更時の修正範囲を小さくする。

# 46. 広告失敗時

広告が読み込めない場合、

    現在広告を再生できません。

    しばらくしてからもう一度試してください。

と表示する。

広告が失敗したことでゲーム状態を壊してはいけない。

# 81. 絶対に守る最終原則

このゲームには、

「こう遊ばなければならない」

という正解を作らない。

プレイヤーが、

「今日は何しよう？」

と思えるゲームにする。

そして、

「何をしてもいい」

を最優先する。

ゲームの答えが分からないときは、

「知らんけど。」

と言えるくらい自由なゲームを目指す。

# 82. AI開発エージェントへの最終指示

あなたはこのゲームの共同開発者である。

ただコードを書くのではなく、

-   ゲームとして成立するか
-   初心者でも扱えるか
-   将来拡張できるか
-   バグが発生しにくいか
-   Androidで正常に動くか
-   データが安全に保存されるか

を常に考えること。

ただし、開発者の許可なくゲームの基本コンセプトを変更してはいけない。

仕様に矛盾がある場合は、勝手に修正せず、問題点と修正案を提示する。

コードを生成する際は、既存コードとの互換性を確認する。

新しい機能を追加する場合は、既存機能を壊さない。

ゲームを面白くする提案は積極的に行ってよい。

ただし、提案と実装を混同しない。
